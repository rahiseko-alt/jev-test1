## なぜ React Router なのか

- **Remix 2 の後継が React Router の framework mode である**と、Remix 側が公式に説明している
  <https://remix.run/blog/wake-up-remix>。Remix を使いたいという当初の意図に最も近い
- v8.0.0 は 2026-06-17 に公開済みで、年1回のリリース周期を公言している
  <https://remix.run/blog/react-router-v8>。Remix 3 と違い、安定版が既に存在する
- 週間ダウンロードは約4,790万。壊れたときに情報が見つかる
- 素のNodeサーバーで動かせるため、自前のサーバーやDockerに置きやすい。
  特定の配置先（Vercel等）に依存しない。OSSとして配布するうえで重要
- MIT

Next.js も候補だったが、自前運用の手順が増え、特定の事業者の機能に寄る部分があるため見送った。
利用者が自分のサーバーに置くことを前提とする本アプリでは、素のNodeで動く方を選ぶ。

### v8 で必要になる前提

- Node 22.22 以上
- React 19.2.7 以上
- framework mode では Vite 7 以上
- ESM のみ（CommonJS のビルドは提供されない）

出典: <https://remix.run/blog/react-router-v8> / <https://reactrouter.com/home>

## なぜ Remix 3 を落としたのか

| 理由 | 内容 |
| --- | --- |
| 安定版が無い | npmの`latest`は今も2.17.5。3系は`3.0.0-rc.3` |
| 資料が足りない | 公式ガイド15章のうち7章が未公開（DB・認証・エラー処理・本番運用など） |
| 仕様が動く | SemVer未適用と公式が明言。内部40パッケージは0.x系のまま |
| 実績が薄い | 週間ダウンロード約1.6万 |
| 配置先が読めない | ビルド段階が無い設計で、既存の配置先との相性が未検証 |

10月2日に安定版が出ても、資料が揃い実績が積まれるまでは採用しない。
下の層分けにより、将来乗り換えたくなったときの費用は小さく保つ。

## データベースを2種類にする理由

- **SQLite を既定**にする。利用者が自分のパソコンやサーバーに置くとき、
  データベースを別に立てずにファイル1つで動く方が、試すまでの障壁が低い
- **PostgreSQL を任意**で選べるようにする。複数人で使う場合に必要になる
- Drizzle ORM は同じ書き方で両方に対応でき、移行（マイグレーション）も扱える

## 層の分け方（再掲）

```
packages/
├── core/   フレームワークに依存しない素のTypeScript。生成AIのクライアントを入れない
└── web/    React Router。画面と、入口の聞き取りだけ
```

`core` は Node だけで動き、Vitest で単体テストできる。
画面の土台を差し替えても `core` は書き換えなくて済む。

## 配布のしかた

- `docker compose up` で動く構成を用意する（アプリ + SQLite のファイル置き場）
- 鍵は `.env` で渡す。リポジトリには `.env.example` だけを置く
- Node 22 を直接使う手順も併記する

## Jev が日本語で使い物にならなかった場合

公式が「英語が主で、CJKを含む他言語は同等ではない」と明記している
<https://docs.typesafe.ai/models>。この前提が崩れた場合に備え、
`core/judge` は**判定エンジンを差し替えられる形**にしておく。

判定エンジンに求める形（これを満たせば何でも入れ替えられる）:

```
判定エンジン
  入力: 主張の文、証拠の本文
  出力: 関連するか（0〜1）、立場（支持/否定/どちらでもない/判断できない）、確信度（0〜1）
```

Jevを第一候補として実装し、日本語での一致率が低ければ別の実装に差し替える。
この検証は、実装と並行して実データで行う。
