# 機能分解とMVPの範囲

仕様（Jevベース OSSファクトチェッカー 企画・設計レポート）を、実装できる単位に割った一覧。
「MVP」は §24 に挙がっている最小構成、「後回し」はそれ以降に足すもの。

## A. 入口（唯一、生成AIを使う工程）

| ID | 機能 | 区分 |
| --- | --- | --- |
| A1 | ユーザーの素の入力を受け取る | MVP |
| A2 | 生成AIが質問を重ね、曖昧さを潰す（複数往復） | MVP |
| A3 | 検証する主張を1文にまとめる | MVP |
| A4 | その1文をユーザーに見せて確定する。確定後は生成AIを呼ばない | MVP |
| A5 | 複合的な主張を、検証できる単位に割る | 後回し |

## 仕様を読んで見つかった、先に決めないと詰まる点

### 1. 再検索の検索語を、生成AIなしでどう作るか

§4 の流れでは、③以降は原則として生成AIを使わない。しかし ⑩ で証拠が足りなければ再検索に戻る。
このとき新しい検索語が要る。生成AIを呼ばずに作る方法を決めておかないと、ここで設計が破れる。

考えられる案:

- **案1**: 入口の生成AIに、主張の確定と同時に検索語の候補をまとめて出させ、以降はその一覧から順に使う
- **案2**: 主張の文から機械的に抽出した語（固有名詞・数値・単位）と、否定方向の定型語を組み合わせる
- **案3**: 検索語の生成だけは例外として生成AIの利用を認める

### 2. 長い証拠本文をJevにどう渡すか

Jevは1リクエストの入力に上限がある（現在確認中）。証拠が長文の場合、そのままでは渡せない。
要約すれば生成AIが必要になり、設計思想に反する。機械的に分割して、分割単位ごとに判定し、
結果をまとめる方式が要る。まとめ方（どれか1つでも支持なら支持とするのか等）を決める必要がある。

### 3. 「一部のみ支持されている」をどう出すか

主張が1文のままだと、この判定は根拠を示しにくい。主張を検証できる単位に割ってから
それぞれを判定し、結果が割れたときに「一部のみ支持」とするのが自然だが、
その分割は A5（後回し）に入れてある。MVPでこの判定をどう扱うかを決める必要がある。

### 4. 反証検索の検索語
